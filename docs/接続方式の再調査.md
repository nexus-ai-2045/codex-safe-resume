# 再起動しない再開方法の再調査

確認日: 2026-10-24。

接続のために公式`Codex`を終了・再起動する方式と、専用の起動方法を要求する方式は、`Mac`・`Windows`とも撤去しました。現在のソースには、公式キューへの受付と起動済みアプリの状態確認を共通方式として実装しています。この文書は選定根拠と実測の範囲をまとめたもので、両`OS`の実機受入完了を意味しません。

## 元の実装の確認結果

元の[`CodexReset`](https://github.com/boyso/codex-reset/tree/10def8531262a15d5f00c73ce4264baf0e18290c)には複数の経路があります。

- 既に使える公式の共有接続があれば、そこへ接続します。
- 接続できない場合は、自分用の別サーバーを起動する経路があります。
- 画面操作への切替を許可した場合は、対象会話を開いて入力欄へ継続文を送ります。この経路自体は、接続方式変更のための公式アプリ再起動を必要としません。
- 共有接続の設定を新たに有効化する経路では、公式アプリの再起動を案内しています。

根拠は固定した版の [`AppServerManager.swift`](https://github.com/boyso/codex-reset/blob/10def8531262a15d5f00c73ce4264baf0e18290c/Sources/CodexReset/AppServerManager.swift) と [`AutoContinueEngine.swift`](https://github.com/boyso/codex-reset/blob/10def8531262a15d5f00c73ce4264baf0e18290c/Sources/CodexReset/AutoContinueEngine.swift) です。「再起動する経路しかない」という理解は誤りでした。

画面操作の実装は`Mac`固有の`AppleScript`とアクセシビリティ権限を使います。送信操作の終了を成功として扱っているため、そのまま移植して到達確認済みとはしません。本アプリでの自動画面入力は未採用です。

## 公式の共通送信経路

公式`Codex CLI`には `codex queue --thread <会話ID> --message=<継続文>` があります。公式の [`queue_cmd.rs`](https://github.com/openai/codex/blob/main/codex-rs/cli/src/queue_cmd.rs) は共通の処理へ渡し、[`session_queue_commands.rs`](https://github.com/openai/codex/blob/main/codex-rs/tui/src/session_queue_commands.rs) は `thread/queue/add` を使います。ここに`Mac`と`Windows`で別の継続文送信ロジックはありません。

[`Windows`向け既存ツール](https://github.com/songyb111-gachon/codex-auto-resume-windows/tree/5bd8ff12802d4c08103a48b0beab6241717b6da2)も、この公式コマンドを使っています。対象会話を公式アプリが読み込んでいることを確認し、未読込みなら送らず待つ構成です。`Windows`では、ファイルを使用中の実プロセスを取得する機能で会話の保持者を確認しています。名前に再起動を含む`Restart Manager`という`OS`機能ですが、同ツールの確認処理は一覧取得だけで、再起動機能を呼びません。

## 採用した共通方式

送信は公式の`thread/queue/add`を使用します。`codex queue`の表示用受付文だけでは、取り出されたキューがすぐ消えたときに本アプリの試行と実ターンを一意に結び付けられません。そのため、同じ公式受付へ保存済みの試行`UUID`を`clientUserMessageId`として渡す処理を実装しました。本文は「続けて」のままで、照合用の印は付けません。

起動済み`Desktop`の読取りには、導入済みの公式アプリで確認したプロセス間通信（`IPC`）を使います。会話所有者の照会、読取り用購読、履歴取得と更新番号の照合を行い、実際のターン・待機状態を取得します。保存データベースの候補だけを現在の実行状態へ格上げしません。導入版に依存する形式なので、未知の版・所有者・スキーマは拒否します。

`OS`固有なのは実プロセス・署名・会話の保持者・通信相手の照合です。`Mac`の公式発行元`Team ID`は、[公式のアプリ検証処理](https://github.com/openai/codex/blob/main/codex-rs/cli/src/desktop_app/mac.rs)に定義された`2DC432GLL2`を使います。署名や接続相手を確認できない場合は送信しません。

## 手元で確認した範囲

2026-10-24時点で、次を区別して確認しました。

| 対象 | 確認結果 |
| --- | --- |
| `Windows`に導入済みの公式`CLI` | `codex queue --help`と対応引数を確認 |
| 旧共有接続で起動済みの専用試験環境 | 公式コマンドの一度の受付と同じ会話での応答完了を確認。旧条件での参考実績 |
| 通常の標準入出力接続で既に起動していた`Windows Codex` | 専用試験会話へ`thread/queue/add`を一度送り、試行`ID`に対応する実ターンと応答完了を確認 |
| 通常起動の`Windows`での実行状態 | 実プロセス確認→`IPC`の所有者・更新番号照合→保存履歴との一致を確認 |
| 自然な利用枠回復後の自動送信 | 未実施 |
| `Mac`実機 | ソース取り込み・回帰検査・配布候補ビルドを実施。新しいリソース照合経路での実接続と再開は未確認 |
| 新方式の配布用画面 | `Windows`候補のビルド・起動を確認、両`OS`の受入は未完了 |

通常起動の試験でも、公式`Codex`の終了・再起動・設定変更を行っていません。通常の既存会話には送らず、専用試験会話だけを使用しました。会話`ID`・本文・端末名・画面原本などの非公開証拠は公開しません。

## 受付後と停止時の扱い

キューの受付`ID`は実ターン`ID`ではありません。受付後に実際のユーザー入力と試行`ID`を照合し、初めて到達を記録します。受付応答の喪失、履歴の遅延、矛盾は自動再送せず要確認にします。

全体`OFF`・個別除外・停止後も、自分が送った未処理キューの照合・取消ができる設計です。他の入力は削除しません。自分のキューを削除できても、既に実行側へ取り出された可能性があるため未到達とは断定しません。保持者がいない会話へ強制的に再開要求を出す経路や、再起動・専用起動・認証情報抽出によって不足を補う経路は採用しません。

同一会話への手動の試験要求が通ったことと、自然な5時間・週次枠の回復で監視処理が自動送信したことは別です。両`OS`の残る受入、最新ソースの全テスト、配布用画面、公開前検査とレビューを完了するまで、全テスト完了・安定版・マージ済みとは記載しません。
