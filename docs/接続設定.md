# 接続の仕組みと詳細設定

現在のソースは、起動済みの公式`Codex Desktop`と公式キュー受付を使う共通方式です。接続のための公式アプリの終了・開き直し、専用起動、起動時の環境変数の注入は必要ありません。通常の起動順のまま接続を確認します。

`Windows`の通常起動済み`Codex`では、専用試験会話への一度の要求と同じ会話での応答完了を確認しました。自然な利用枠回復後の自動送信、`Mac`実機、両`OS`の配布用画面の受入は未完了です。ソースの実装、画面の配布物、実機受入は区別します。

## 両`OS`で共通の処理と異なる処理

利用枠・最新ターン・待機状態・個別除外・試行記録・公式キューへの送信・実ターン到達の照合は、`Mac`と`Windows`で同じ処理を使います。送信本文は「続けて」で、照合用の印を本文へ追加しません。保存済みの試行`UUID`を公式の`clientUserMessageId`として渡します。

`OS`ごとに異なるのは、公式アプリの署名・実行ファイル・プロセスの開始時刻・会話を保持しているプロセス・通信相手の確認です。`Windows`ではパッケージ登録・署名と名前付きパイプの接続相手を確認します。`Mac`では公式バンドルの署名と同梱`CLI`の内容を照合し、所有者・権限を確認した`Unix`ソケットの接続相手を確認します。

`Mac`の同梱`CLI`には単体署名がない場合があります。その場合は公式アプリ全体の厳格な署名確認に加え、署名で保護された`CodeResources.files2`の正確なパスと`hash2`を使い、実ファイル全体の`SHA-256`が一致する場合だけ認めます。欠落・未知形式・リンク・不一致では送信しません。内包された署名済みコードには個別の発行元確認も適用します。根拠は[公式の署名仕様](https://developer.apple.com/library/technotes/tn2206/)と[リソースハッシュの仕様](https://developer.apple.com/documentation/technotes/tn3126-inside-code-signing-hashes)です。これは同梱内容の一致の検証であり、単体署名・公証・実行後のメモリー完全性を保証するものではありません。

`Mac`の公式発行元`Team ID`は`2DC432GLL2`を使います。根拠は[公式のアプリ検証処理](https://github.com/openai/codex/blob/main/codex-rs/cli/src/desktop_app/mac.rs)です。実機でその確認に失敗した場合は送信せず、検証を省略して対応済みとは扱いません。

## 現在のチャット状態の確認

一覧用の保存データベースは読取り専用です。履歴に利用枠エラーがあるだけでは、送信対象として認めません。

1. 起動済みの公式アプリと、そのアプリが使う保存先・公式`CLI`を確認します。
2. 対象会話をそのアプリが既に保持していることを確認します。未読込みなら送らず待ち、`thread/resume`で強制的に開きません。
3. プロセス間通信（`IPC`）で現在の会話所有者を探し、読取り用の購読と履歴取得を行います。所有者・会話・対応版・更新番号（`revision`）が一致する実行状態だけを採用します。
4. 保存履歴の反映が最新であり、最新ターン・状態が実行状態と一致することを確認します。最後に実プロセスを再確認します。

`IPC`の未知の形式、実行中、承認待ち、入力待ち、不一致、履歴の反映遅延は送信を止めます。接続できない場合に自動画面入力や別の会話の起動へ切り替えません。

## 受付と到達の区別

送信には公式の`thread/queue/add`を使います。`codex queue`と同じ受付処理で、保存済みの試行`ID`を指定できる経路を使用します。公式`CLI`の短命な標準入出力接続は、利用枠の読取りとキュー操作に限り、別の会話を開始・再開する用途には使いません。

キュー受付、実ターンへの到達、応答完了は別の段階です。受付`ID`をターン`ID`として保存しません。試行`ID`と公式のユーザー入力・実ターンを照合して到達を確認し、受付応答を失った場合も同じ試行を自動で送り直しません。

全体`OFF`・個別除外の後は、既に送った自分のキューを照合します。通常終了の要求時も、先に新規送信を停止して送信処理と残る要求を確認します。プロセスが終了した後に照合が継続する保証はありません。取消は試行`ID`・受付`ID`・「続けて」の入力が一致する一件だけを対象にします。公式アプリが不在の場合も、保存済みの公式`CLI`の配置・`SHA-256`を再確認できる場合だけ照合・取消を認め、新しい送信と実行状態の確認は認めません。削除成功だけで未到達とは断定せず、不明な試行は要確認として保持します。

到達を確認できていない試行が残る間は、照合に必要な接続設定の置換を拒否します。保存先や公式`CLI`の対応を失ってから別接続へ切り替えません。公式に保存される空の`text_elements`は、[公式の入力形式](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/user_input.rs)に従って通常の文字列入力と同等に扱い、未知の追加項目や空でない特殊要素は取消対象にしません。

## 接続設定と同意

保存するのは公式`CLI`の場所・`SHA-256`・対象の保存先・接続確認と操作ルールへの同意です。認証は公式`CLI`が管理し、`token`・`cookie`・認証ファイルはコピーしません。

接続の準備だけでは、監視や送信を有効にしません。送信には現在の公式アプリとの対応、保存した公式`CLI`の同一性、接続先と操作ルールへの確認、全体`ON`、対象チャットの選択が必要です。`CLI`が更新された場合は確認をやり直し、別の実行ファイルへ自動で切り替えません。

画面や設定の旧版から移行する場合も、公式`Codex`の設定や起動方法は変更しません。両`OS`の配布用画面の受入は未完了のため、現時点で既存配布物の操作手順だけで新方式を利用できるとは案内しません。

## 画面のプラン・接続・利用枠

一覧・利用枠の読取り、公式アプリとの接続、送信許可は別々に確認します。利用枠は公式`account/rateLimits/read`から読み、枠の期間に従って5時間・週次を分類します。返されない枠を0％・100％・無制限として補いません。表示用の取得結果やアカウント比較だけで、再開送信を許可しません。

5時間枠と1週間枠は常に表示し、`API`実測とプラン案内を区別します。前回取得から120秒を超えた値や取得失敗は更新待ちとして扱います。残量ゲージは容量であり、回復までの時間の進捗ではありません。

プラン案内の表示用正本は`plan_metadata.py`です。[公式の利用枠案内](https://learn.chatgpt.com/docs/pricing)の確認日を表示し、古い案内や取得できない値を送信許可の代用にしません。認証情報やアカウント識別子を画面・ログへ出しません。

## 確認後の選び直し

全体の自動再開を`OFF`にし、一覧の「すべて」で対象の行を選びます。「選択チャットの操作」→「確認して選び直す（試行履歴は保持）」は、本人が`Desktop`側の現在のチャット状態を確認した後の操作です。「要確認」または「完了」で選択解除されている対象だけを初期待機へ戻します。監視は自動で有効になりません。実行中・送信確認中の対象には使えません。

選び直した後は、行を選んで「選択チャットの操作」→「選択したチャットを対象にする」、または「このチャットを自動再開の対象にする」で対象を指定します。他の行の対象指定は変更せず、全体`OFF`の間は送信しません。

過去の送信試行の記録は保持します。この操作後も同じ失敗ターンへの自動再送は行いません。送信結果が不明な場合は`Desktop`側を確認し、必要な手動対応を済ませてください。

### `CLI`で確認して選び直す

`GUI`の代わりに`CLI`を使う場合は、指定した対象の状態と世代を先にプレビューします。既定の一覧出力には識別情報を追加しません。

```sh
python app.py mark <対象ID> idle --dry-run
```

`Desktop`で対象の状態を確認した後、プレビューに表示された世代を指定して戻します。世代が変わっていれば操作は停止し、再確認が必要です。

```sh
python app.py mark <対象ID> idle --expected-generation <確認した世代>
python app.py enable <対象ID>
```

プレビューは監視状態や試行履歴を変更しません。`--dry-run` と `--expected-generation` は同時に使えず、選び直しの `idle` 専用です。監視を有効にする操作は別です。

## 安全性の範囲

提供された利用枠に加えて、公式の利用許可と支出制限も確認します。週次枠一個だけの応答も、アカウントに対応する利用許可・支出制限・期間が明示される場合に限って扱います。利用許可が不明・満杯・制限理由ありなら送信しません。

送信直前にも同じ対象の利用枠・最新の制限停止・待機状態・キュー・監視承認を再確認します。通常完了・手動操作・承認待ち・入力待ちは停止条件です。ただし、確認と送信を`Codex`側で一体にする原子的な排他は保証しません。監視対象を手動操作する前には全体`OFF`にしてください。

ローカルの模擬検査や、専用会話への一度の送信成功を、実際の利用枠回復後の自動再開成功へ読み替えません。両`OS`の自然な利用条件で受入を行うまで安定版とは呼びません。

### 読取り接続の使い分け

`Mac`・`Windows`とも、会話の状態を一度取得したら、その読取り用接続を閉じます。次の取得では同じ検証済みの公式プロセスへ新しく接続し、前回の接続に残った差分通知を持ち越しません。公式アプリのプロセスと送信用の接続情報は維持し、公式アプリの終了・再起動や接続設定の書換えは行いません。

会話所有者、通信の版、履歴の更新番号、実ターンと状態、接続先の実体は従来どおり照合します。失敗時も今回の読取り接続を閉じ、古い観測を代用したり、送信済みの要求を再送したりしません。

読取り接続の終了処理が失敗した場合は、その観測も成功扱いにせず、接続情報を無効にして後続の読取りと新しい送信を停止します。失敗した接続は再利用しません。

## 旧方式の撤去

`Mac`・`Windows`とも、再起動・専用起動・起動時の環境変数注入を前提とする接続方式は廃止しています。旧中継の回帰テストや安全な残存物の回収処理は、現行の接続手順とは分けて保持します。旧方式の成功を、新方式の受入実績には数えません。
