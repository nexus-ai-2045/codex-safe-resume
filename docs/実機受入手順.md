## 実施条件

対象は本物のCodex Desktopです。CLIだけでターンを開始した結果、模擬bridge、CI、接続先の存在、HTTP成功だけでは実機受入になりません。接続未設定時は送信を停止します。接続設定を行い、同じDesktopへの要求と画面の読戻しを確認するまで正の再開シナリオは未達とします。監視対象を手動操作する前に監視を停止し、完全同時操作の原子的排他を保証する受入とは区別します。

各端末のCLI診断と本人の画面確認を組み合わせます。Computer Useは本人が許可したアプリ・操作・フォーカス範囲に限ります。認証情報の抽出や保護された操作の迂回は行いません。自然な利用枠停止を使い、枠を使い切るための無駄な処理を生成しません。

## 診断と記録

対象のコードSHAと配布物ハッシュ、OS、PythonとCodex Desktopの版を記録します。ソースから `python diagnose.py --json` を実行し、読取り・依存・接続先を確認します。診断の成功コードや接続先の存在は、送信可能や実機再開成功を意味しません。

検証用チャットは「選択A」と「未選択B」のような別名で記録します。実ID、会話名、会話本文、メール、端末名、ユーザー名、絶対ホームパス、スクリーンショット原本はGitHubへ添付しません。本人の画面確認は、確認対象・時刻・コードSHAを明示して受領し、AIが確認済みに書き換えません。

## 各OSの確認順

1. 配布スクリプトでユーザー領域に配置し、アイコンから起動できることを確認します。WindowsはPowerShell 7以降を使用します。自動起動やレジストリ変更がないことを確認します。初回は通常ウィンドウが開き、検索・自動再開ON/OFF・設定が画面内に収まること、サイズ変更後も主要操作が隠れないことを確認します。
2. Macは画面上部のメニューバー、Windowsはタスクトレイの実アイコンを確認し、×で隠した後の再表示とメニューからの終了を確認します。MacではDockからの再表示も確認します。「常駐中」の文字列だけで実アイコンの成功としません。常駐できない場合は画面を残して終了操作を案内し、終了に失敗した場合は終了済みと扱いません。
3. 全体の自動再開をOFFにして一覧の「すべて」を選び、未選択Bの行で「このチャットを自動再開の対象にする」を外します。選択Aの行を選び、「設定」→「選択したチャットだけON」で対象にしてから全体をONにします。このメニュー操作は他のチャットを解除しないため、送信対象にしないチャットは個別に除外します。本当の5時間制限による停止を観測し、現在の提供枠と利用許可を照合してから、解除後に同じチャットへ一度だけ再開されることを本人が確認します。未選択Bへは送信しません。公式応答が週次1枠だけの場合は、[接続設定の利用許可条件](接続設定.md)に従い、未提供の5時間枠を検証済みとして記録しません。
4. 本当の週次制限と両枠の競合、2度目の制限後の再開を確認します。解除時刻だけを根拠に送信しないことを確認します。
5. 完了、承認待ち、入力待ち、キャンセル、手動の別ターンで送信が止まることを確認します。
6. アプリ再起動、スリープ復帰、二重起動、送信応答喪失を検証します。不明な送信を再送せず、要確認として保持することを確認します。
7. アプリを終了して本体を削除し、Codexと会話・設定が保持されることを確認します。設定削除は別の明示操作で確認します。未知の追加ファイルやリンクは保持して停止します。

## 証拠と未達の扱い

移行後リポジトリの受入課題には、匿名化した条件、対象SHA、実行した検査、本人確認、確認できなかった範囲、次の操作を記録します。移行前のIssue #11は過去の記録であり、同じ番号のURLを新しい台帳とみなしません。現行リポジトリの不変IDと課題の存在を確認してから対応付けます。WindowsでPowerShellを実行しただけではWindows DesktopのE2Eになりません。利用枠の解除待ちや接続経路の不足がある間は受入課題を閉じません。

### 一覧とチャット別の操作の確認

送信前に通常画面の全体ON/OFFと、5時間・1週間の残量・回復日時・あと何時間の表示を確認します。接続は起動済みDesktopへ確認し、Desktopの終了・再起動・専用起動を要求しないことを確認します。操作ルールの同意、拒否・取消し・未対応を区別し、取消し後に設定保存・遅延ON・送信をしないことを確認します。通常画面の「再開待ち」「要確認」「すべて」を切り替え、詳細の検索条件を隠れたまま適用しないことを確認します。将来見つかった別チャットの利用枠失敗も自動で対象化すること、通常一覧の上限外でも検出すること、個別除外・不明送信・旧完了行を勝手に復活させないことを確認します。

以下は全体の自動再開をOFFにしてから行い、各操作後も全体OFFのままで送信しないことを確認します。「設定」の区切り線の下にある「チャット別の操作」を使います。一括選択の画面操作はありません。

1. 全体OFFのままアプリを開き直し、行を選ぶ前に、行が必要な以下の操作を押すと日本語で行の選択を案内することを確認します。その後、一覧の「すべて」を選びます。
2. 任意の列名を押して並べ替えた後、「設定」→「実行・監視中を上に戻す」で優先順へ戻ることを確認します。この操作には行の選択は不要です。
3. 完了・要確認・送信処理中ではないチャットの行を選び、「設定」→「選択したチャットだけON」で、その行が再開対象になることを確認します。他の行の対象指定は変わりません。下の「このチャットを自動再開の対象にする」で個別の除外と復帰も確認します。
4. 「設定」→「完了として記録（監視を終了）」を選び、確認ダイアログを取り消すと状態が変わらず、承諾すると完了になり監視対象から外れることを確認します。別の行で「設定」→「要確認として記録（自動再開を停止）」も同様に確認します。
5. 完了または要確認の行を選び、公式Desktopで実行・承認待ちの終了と現在の接続先を確認してから、「設定」→「確認して選び直す（試行履歴は保持）」を選びます。取消しでは変更せず、承諾後も監視は無効で、対象を選び直す必要があり、過去の試行履歴を保持することを確認します。完了・要確認以外では選び直しを拒否することも確認します。
6. 行を選び、「設定」→「詳細情報（ID・場所）」でその行の情報を確認します。実IDや絶対パスは受入記録へ転記しません。

回復予定が未取得なら理由を表示し、枠情報の取得後に反映されることを確認します。回復予定日時の表示は、実際に「続けて」が届いた証拠とは分けて記録します。
